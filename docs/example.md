# 系统测试计划 — Tuner-mock 框架（目标：“波科”项目数据）

目的

- 验证 mock 数据框架能为目标项目（“波科”系统）生成真实、有关联的测试数据集，以供系统测试使用。本计划仅聚焦框架的造数能力，明确排除重审业务逻辑与性能压测场景。

范围

- 输入：代表性的 DDL（表结构）和最小量主数据样例。
- 输出：生成的数据集（发票、销量、披露类记录等）以及可直接入库的导出产物（CSV/SQL）。
- 排除项：审计业务逻辑、重审触发、以及负载/性能测试。

目标

- 验证 DDL → models 的转换正确并能产出经 `pydantic` 校验的模型。
- 验证生成器能产出可与主数据关联的发票及发票明细。
- 验证生成器能产出包含大量明细并将销量明细与发票建立 N:M 关联的销量数据。
- 验证 rules/plugin 能表达预期的关联与约束。
- 验证可复现生成（基于 seed）和流式导出（避免 OOM）。

覆盖层映射（框架层）

- `infrastructure`：读取 DDL / 写 CSV/SQL / 导入辅助脚本
- `models`：从 DDL 生成的 `pydantic`/ORM 模型
- `rules`：生成过程中用于建立关联和约束的插件
- `generators/engine`：实体生成、关联建立、随机种子控制与导出
- `expectations`：可选层，生成输出的断言或期望结果

测试用例

1. DDL → 模型生成

- 目标：将波科示例 DDL 转换为框架模型并验证模型实例完整性。
- 步骤：准备小型 DDL；运行 `ddl2models` 脚本；检查生成模型；用生成器在严格校验下实例化示例对象。
- 预期：生成模型可通过校验并满足后续测试所需字段和类型。
- 覆盖：`infrastructure`、`models`。

2. 发票生成与主数据关联

- 目标：生成发票及明细，并确保其能关联到指定的主数据（如供应商、商品主数据）。
- 步骤：准备主数据（小表）；运行发票生成器（规则引用主键）；导出 CSV；小规模导入测试库并验证关联。
- 预期：发票行引用现有主数据主键；发票明细条数符合配置；基本完整性校验通过。
- 覆盖：`models`、`rules`、`generators`、`infrastructure`。

3. 销量生成并与发票建立关联（N:M）

- 目标：生成销量记录，使每条销量明细可关联多条发票明细，且发票明细可被多条销量明细引用。
- 步骤：配置多对多关联规则；在同一次运行中生成销量及发票数据；导出并导入测试库，执行查询验证链接关系。
- 预期：按配置采样（例如 10% 的销量明细）存在关联的发票列表；逻辑层面参照完整性通过检查。
- 覆盖：`rules`、`generators`、`models`。

4. 大明细场景（功能性规模，非性能压力）

- 目标：确保生成器以流式方式生成单条销量含大量明细并关联大量发票时不发生内存耗尽。
- 步骤：流式运行生成器，设置大明细数量；产出文件并抽样验证记录。
- 预期：生成器能在受控内存下完成，产出文件可批量导入。
- 覆盖：`generators`、`infrastructure`。

5. 导出与 DB 导入就绪性

- 目标：产出文件适配常见批量导入工具（CSV 或 SQL COPY）。
- 步骤：导出 CSV/SQL；执行导入脚本（或干运行解析）并验证行数与基本约束。
- 预期：产物可导入，提供导入命令示例，小规模导入成功。
- 覆盖：`infrastructure`。

6. 可复现性与确定性

- 目标：在固定 seed 与配置下，生成过程应可复现。
- 步骤：使用相同 seed 与配置运行生成器两次，比较输出文件校验和或哈希。
- 预期：输出一致（位级别或断言级别）。
- 覆盖：`generators`。

验收标准

- 每个测试用例需提供自动化脚本以执行生成并完成声明的校验。
- 对生成器、模型映射或规则表达能力的问题应创建 issue 并跟踪修复。
